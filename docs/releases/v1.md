# v1 Release Acceptance

Updated: 2026-10-14

Status: planned; not release-ready.

This document defines v1 scope, acceptance criteria, validation evidence, and
release progress. The [roadmap](../status/roadmap.md) holds product direction;
the [feature tracker](../status/features.md) remains authoritative for individual
feature implementation state. Feature references define the detailed contracts.

v1 is a planning milestone, not an already published version. The package
currently uses version `0.1.0`; the final release version and delivery policy
are not yet established.

## Goal and scope

Deliver one complete path: initialize a project -> maintain SQL files ->
generate a query manifest from the target database schema -> run the server
with the project settings and manifest -> authenticated REST discovery and
execution with JSON. PostgreSQL and SQLite must both pass acceptance.

| Included capability | Contract / implementation tracking |
|---|---|
| Settings, secrets, backend pools, normalized results, and JSON envelope | [Feature tracker](../status/features.md) |
| SQL query validation and binding | [SQL query contract](../features/sql-query-contract-feature-reference.md) |
| CLI command dispatch, project paths, and command error behavior | [CLI feature](../features/cli-feature-reference.md) |
| Project initialization CLI, including settings templates, ignored local configuration/secrets, and a copyable `AGENTS.md` | [Project initialization](../features/project-initialization-feature-reference.md) |
| Database schema introspection used by manifest generation | [Schema introspection](../features/schema-introspection-feature-reference.md) |
| Manifest generation and query classification | [Query manifest](../features/query-manifest-feature-reference.md) |
| Bound execution and query limits | [Query executor](../features/query-executor-feature-reference.md#planned-bound-execution) |
| Server startup using project settings and the generated manifest; REST JSON discovery, details, execution, and a published OpenAPI document | [REST middleware](../features/rest-middleware-feature-reference.md) |
| Static bearer token, required on every request | [REST middleware](../features/rest-middleware-feature-reference.md#3-authentication-and-caller-metadata) |

The intended project workflow is:

```text
sqlbinder init <project-directory>
sqlbinder generate-manifest --project <project-directory>
sqlbinder server --project <project-directory>
```

These command forms are illustrative, not finalized CLI syntax. `init` should
create a project directory containing `.gitignore`, `AGENTS.md`, `settings.toml`,
`settings.local.toml`, an empty `db.local.pwd` file, and a `queries/` directory.
The generated `settings.local.toml` points to `db.local.pwd` through the
existing `database.password_file` setting. The local settings file and
password file are ignored by Git;
templates, SQL files, and `manifest.json` are intended to be version-controlled.
`manifest.json` is generated at the project root. No schema-snapshot file is
required by this workflow: `generate-manifest` connects to the configured
database and inspects its schema. `server` loads the settings and manifest and
does not regenerate the manifest at startup.

The scaffold must not contain a real or pretend credential. Users supply the
password file locally or mount a container secret at its configured path. The
CLI must not require users to put passwords in chat or pass them as ordinary
command-line arguments. The initial credential source is file-based; key vault
and IAM providers are possible future extensions, not part of v1. Whether
generation and runtime use separate credentials remains open below. The
generated `AGENTS.md` is project
guidance for coding agents, not an executable contract; it must direct agents
to the CLI for validation and must not encourage exposing credentials.

Not included: protobuf or Rust type generation, REST with protobuf, gRPC,
service-session authentication, admin endpoints, full observability
(metrics/tracing), audit events, container packaging, delivery and usage
guides, pagination, streaming, or multi-query transactions. V1 does include
minimal structured request logs for operation outcomes and optional
`user_id`/`span_id` correlation values; these values are caller-supplied and
are not verified identity. See the [feature tracker](../status/features.md)
for future targets.

The static key gives every caller the same full access. v1 is intended for
trusted networks only, using database credentials with the minimum privileges
the queries need. It does not promise per-user authorization or infrastructure
security. API callers must never supply SQL.

## Progress and evidence rules

Release gates use `Pending`, `In progress`, `Passed`, or `Blocked`. `Passed`
requires linked evidence for the candidate being assessed; an implemented
feature alone does not pass a release gate. Missing dependencies, all-skipped
runs, and absent measurements cannot count as passes.

Update the relevant gate in the same change that alters release readiness.
Record failures and unresolved decisions, not just successful runs. Update the
feature tracker separately when implementation state changes. A new candidate
must rerun affected gates; identify any reused evidence and explain why it
still applies.

| Gate | Requirement | State | Evidence / remaining work |
|---|---|---|---|
| V1-G1 | Included scope implemented and blocking contract decisions resolved | Pending | Project init, live-database manifest generation, bound execution, limits, server/API, and authentication remain planned in the [feature tracker](../status/features.md) |
| V1-G2 | Functional checks and both backend integration suites pass | Pending | Existing [test targets](../../tests/README.md) are not candidate acceptance evidence |
| V1-G3 | All required E2E journeys pass on both backends | Pending | No service E2E runner or candidate results established |
| V1-G4 | Approved benchmark budgets pass on the reference environment | Pending | Workloads, numerical budgets, harness, and baseline results pending |
| V1-G5 | Required test suites pass in CI for the candidate | Pending | CI policy and workflows are not finalized |
| V1-G6 | Candidate evidence reviewed; release blockers resolved | Pending | Candidate identity, compatibility review, known issues, and approval pending |

## Functional acceptance

All items below are required. Use unit tests for local rules and integration
tests against both real backends wherever database semantics apply. E2E tests
verify wiring and user-visible outcomes rather than replacing those tests.

| ID | Observable acceptance outcome |
|---|---|
| V1-F1 | Invalid settings and unreadable or invalid secret inputs produce explicit errors; credentials and secret contents are not exposed in responses or diagnostics |
| V1-F2 | `init` creates the documented project template without overwriting existing user files by default; local settings and `db.local.pwd` are Git-ignored, no credential is generated, and the copied `AGENTS.md` gives accurate CLI and credential-safety guidance |
| V1-F3 | Manifest generation connects to the configured database using an approved credential source and read-only schema-inspection access; it enforces the SQL contract, classifies every supported operation, and rejects invalid or unresolvable contracts with a nonzero exit and actionable diagnostics; failure never writes a partial manifest or corrupts an existing manifest |
| V1-F4 | Identical SQL, observed schema, and previous manifest produce byte-identical manifests; query identities and change handling follow the approved manifest contract |
| V1-F5 | The server loads settings and the generated manifest from the selected project, connects to the configured runtime database, and serves without modifying or regenerating the manifest |
| V1-F6 | Runtime discovery exposes registered queries from the generated manifest; execution resolves those identities, binds typed values without SQL interpolation, and never executes client-supplied SQL |
| V1-F7 | Reads and writes with `RETURNING` produce the declared row output; writes without `RETURNING` produce the declared affected-row result; empty results, nulls, aliases, and types match the approved contract on both backends; decode failures are errors, not null substitutions |
| V1-F8 | Missing or incorrect bearer tokens are rejected on every endpoint without revealing query data or changing database state; correct tokens allow supported operations |
| V1-F9 | Unknown queries, missing/extra/wrong-type parameters, and database failures produce the approved API error status and body, not success-shaped responses; rejected inputs do not execute SQL |
| V1-F10 | Configured timeouts and result-size limits are enforced at their documented boundaries; timeout cancels the query and releases its connection, and subsequent valid requests succeed without restarting the service |
| V1-F11 | Structured request logs include the operation identity when known and request/operation outcome and HTTP status; supplied `user_id` and `span_id` are recorded only as untrusted correlation metadata; credentials, raw SQL, and parameter values are not logged |
| V1-F12 | A published OpenAPI document describes every implemented public API and health/readiness endpoint, including routes, methods, authentication, request/response schemas, and errors; it matches the running service |

Exact CLI syntax, HTTP routes, request/response schemas, token configuration,
and error codes must be specified before their
tests are implemented. This document does not invent those interfaces.

## E2E acceptance

Exercise the built CLI and actual running service through their public
interfaces, using generated manifests and real PostgreSQL and SQLite
dependencies. Internal function calls and mocked core responses are not E2E
evidence. Run each journey independently on each backend.

| ID | Journey and oracle | State |
|---|---|---|
| V1-E1 | Initialize a project in a test-owned directory; assert expected template files, ignored local settings/secrets, no generated credential, and no overwrite of pre-existing files | Pending |
| V1-E2 | Generate a manifest by connecting to a test-owned PostgreSQL or SQLite database with valid SQL; start the server from that project, authenticate, discover expected query identities, and execute a parameterized read; assert exact contract-defined JSON values, types, aliases, and count | Pending |
| V1-E3 | Execute registered insert, update, delete, and upsert queries; verify exact affected-row/`RETURNING` responses and persisted effects through public reads, including empty and nullable results | Pending |
| V1-E4 | Generate from invalid SQL, inaccessible schema, or an unresolvable contract; assert nonzero CLI exit, useful redacted diagnostics, and no partial output or corruption of a previous manifest; repeated valid generation against the same schema is byte-identical | Pending |
| V1-E5 | Call every endpoint with missing and wrong bearer tokens, then valid tokens; assert approved rejection responses, no data disclosure or mutation on rejection, and successful authorized requests | Pending |
| V1-E6 | Submit an unknown identity, invalid parameter sets, and SQL-looking parameter values; assert defined errors or literal-value binding as appropriate, and no unintended database effects | Pending |
| V1-E7 | Induce a controlled database execution failure, timeout, and result-limit breach; assert defined errors and a successful subsequent valid request after restoring the dependency where necessary; cover just-below, at, and above configured size boundaries | Pending |
| V1-E8 | Make requests with and without `user_id` and `span_id`; verify structured logs correlate the supplied values with operation identity and outcome/status, treat them as untrusted, and redact tokens, SQL, and inputs | Pending |
| V1-E9 | Validate the published OpenAPI document and compare it with the running service so every public route, method, authentication requirement, schema, error response, and health/readiness endpoint is represented accurately | Pending |

Use test-owned directories, data, database instances, and processes. Verify
readiness with bounded checks; bound requests and teardown. Do not reset a
shared database or stop unrelated services. Always clean up owned resources,
including after failures, and retain redacted diagnostics and exit statuses.
Current PostgreSQL integration tests share mutable fixture state and must run
serially; do not reuse that state concurrently for E2E or benchmarks.

## Benchmark acceptance

Performance is a separate gate from correctness. These are required measurement
scenarios, not claims that a harness or acceptable performance already exists.

| ID | Scenario / measured boundary | Required metrics | State |
|---|---|---|---|
| V1-B1 | CLI process start through completed manifest generation for agreed small and large query sets | Elapsed time, peak process memory | Pending |
| V1-B2 | Bound executor call through normalized result, with pool/fixtures prepared outside timing; measure JSON serialization separately | Operation latency, peak process memory, output rows/bytes | Pending |
| V1-B3 | HTTP request through complete JSON response for parameterized reads and supported writes at agreed result sizes and concurrency | Per-request p50/p95/p99 latency, successful requests/sec, errors, peak service memory | Pending |
| V1-B4 | Service process start through externally verified readiness, with database readiness established first | Startup elapsed time, peak service memory | Pending |

Both backends need results. Before full runs, approve and record:

- dataset/query counts, input distributions or seed, result sizes, operation
  mix, concurrency, and database/pool/limit configuration;
- reference hardware/OS, release profile, toolchain, database versions, and
  load-generator arrangement;
- warm-up, independent repetitions, sample counts, maximum duration, and
  CPU/memory/storage budget; keep cold-start and steady-state results separate;
- numerical latency, throughput, memory, and startup budgets for each scenario,
  baseline identity, allowed regression, and comparison/noise policy.

Budgets are **TBD and release-blocking** until approved. Derive proposals from
representative usage and recorded baseline measurements; do not invent
thresholds or silently relax them after a failure. This document authorizes no
heavy benchmark runs or host tuning.

Validate outputs and persisted effects independently of timing. Failed or
incorrect operations cannot count as successful throughput. Record raw samples,
errors, environment metadata, exact commands, and candidate identity. Use
per-request observations for latency percentiles, not aggregate throughput.
Report variation and inconclusive comparisons; preserve all runs. Hosted CI
smoke measurements are not a substitute for controlled performance evidence.

## Candidate evidence and go/no-go

No candidate has been assessed. For each candidate, record:

- revision and dirty-state identity, intended version, artifact identity,
  toolchain/profile/features, and tested backend/platform configuration;
- each gate's exact commands, executed scenarios, results, skips/failures,
  and links to logs, CI runs, raw benchmark data, and environment metadata;
- configuration, manifest, library API, and HTTP compatibility changes, with
  migration requirements or explicit limitations;
- known issues affecting included scope, their impact, workarounds, and any
  explicitly approved exception with rationale.

Release only when V1-G1 through V1-G6 pass. Required correctness journeys and
unresolved performance budgets remain blockers; documenting a workaround
alone does not turn a failed gate into a pass. Any change to acceptance scope
must be explicit and reviewed before the go/no-go decision.
